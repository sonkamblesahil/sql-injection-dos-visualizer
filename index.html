🛡️ How Resource-Intensive Queries Crash Servers

Resource-intensive SQL injection attacks exploit database queries to consume excessive CPU, memory, and I/O resources:

🔴 Attack Techniques

-- 1. Cartesian Product (Exponential Row Multiplication) SELECT * FROM users a, users b, users c, users d -- If each table has 10,000 rows: 10,000^4 = 10,000,000,000,000,000 rows! -- 2. CPU-Intensive Functions SELECT BENCHMARK(100000000, MD5('payload')) -- Forces CPU to compute MD5 hash 100 million times -- 3. Time-Delay Exploitation SELECT SLEEP(10) FROM users -- Blocks thread for 10 seconds per row -- 4. Recursive CTEs (Infinite Loops) WITH RECURSIVE cnt(x) AS ( SELECT 1 UNION ALL SELECT x+1 FROM cnt LIMIT 100000 ) SELECT * FROM cnt -- 5. Nested Subqueries (Memory Exhaustion) SELECT * FROM ( SELECT * FROM ( SELECT * FROM users ) a ) b

💥 Why They Crash Servers

  • Cartesian Products: Joining 4 tables with 10k rows each creates 10^16 potential rows - exponential explosion
  • BENCHMARK/SLEEP: Forces CPU/threads to work or wait, exhausting the connection pool
  • Memory Exhaustion: Query tries to store massive result sets in RAM
  • I/O Saturation: Excessive disk access locks the database
  • Thread Pool Depletion: All database worker threads are blocked, preventing legitimate queries
  • Connection Starvation: Application can't get new database connections

🛡️ Defense Solutions

1. Parameterized Queries (Primary Defense)
// ❌ VULNERABLE: User input directly in query const query = "SELECT * FROM users WHERE id = " + userInput; // ✅ SAFE: Input treated as data, not code const query = "SELECT * FROM users WHERE id = ?"; db.query(query, [userInput], callback); // Node.js example const result = await pool.query( 'SELECT * FROM users WHERE id = $1', [userId] );
2. Input Validation and Whitelist
// Only allow expected characters/patterns const userId = parseInt(req.query.id); if (!Number.isInteger(userId) || userId < 0) { return res.status(400).send("Invalid input"); } // Whitelist approach for strings const allowedColumns = ['name', 'email', 'created_at']; if (!allowedColumns.includes(sortColumn)) { throw new Error("Invalid column"); }
3. Query Timeouts (Prevent Resource Exhaustion)
-- MySQL: Limit max query execution time SET SESSION max_execution_time = 5000; -- 5 seconds -- PostgreSQL: Statement timeout SET statement_timeout = '5s'; -- Application level timeout (Node.js) db.query(query, {timeout: 5000}, callback);
4. Database User Privileges (Least Privilege)
-- Create limited application user CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'password'; -- Grant only necessary permissions GRANT SELECT, INSERT, UPDATE ON app_db.* TO 'app_user'@'localhost'; -- Revoke dangerous functions REVOKE EXECUTE ON FUNCTION BENCHMARK FROM 'app_user'@'localhost'; REVOKE EXECUTE ON FUNCTION SLEEP FROM 'app_user'@'localhost';
5. Connection Pool Limits
-- Database level SET GLOBAL max_connections = 1000; -- Application pool configuration (Node.js) const pool = mysql.createPool({ connectionLimit: 10, waitForConnections: true, queueLimit: 0, acquireTimeout: 10000 });
6. Query Monitoring and Alerts
-- Monitor slow/expensive queries SHOW PROCESSLIST; -- Kill dangerous queries KILL QUERY process_id; -- Enable slow query log SET GLOBAL slow_query_log = 'ON'; SET GLOBAL long_query_time = 2; -- Check current queries SELECT * FROM information_schema.processlist WHERE time > 5;
7. Rate Limiting at Application Level
// Express.js rate limiting const rateLimit = require('express-rate-limit'); const limiter = rateLimit({ windowMs: 60 * 1000, // 1 minute max: 30, // 30 requests per minute standardHeaders: true, legacyHeaders: false }); app.use('/api/', limiter);
8. Web Application Firewall (WAF)
  • Deploy WAF rules to detect SQL injection patterns
  • Block requests containing suspicious keywords (BENCHMARK, SLEEP, UNION, etc.)
  • Use services like Cloudflare, AWS WAF, or ModSecurity
  • Implement request signature validation
